# แผนปรับระบบบันทึกหลังสอนและออก PDF

> อัปเดต 24 ตุลาคม 2569: ขั้นตอนบันทึกปัจจุบันใช้สรุปและยืนยันครั้งเดียวตามระดับที่เลือก โดย PDF เป็นทางเลือก แผนเดิมด้านล่างเก็บไว้เป็นประวัติ ดูขั้นตอนใช้งานล่าสุดใน [docs.md](../docs.md)

วันที่วิเคราะห์: 15 ตุลาคม 2569

สถานะอัปเดต 17 ตุลาคม 2569: ลงมือพัฒนา workflow หลักแล้ว รายละเอียดแผนด้านล่างเก็บเป็นข้อกำหนดอ้างอิง; ไม่ได้หมายความว่ารายการเสริมทุกข้อเปิดใช้แล้ว

### ผลการพัฒนารอบนี้

- Workspace สร้าง/แก้ร่วมกัน, server draft, autosave, resume, optimistic locking และ source conflict
- API/fallback กลุ่มและรายชื่อ พร้อม pagination; รายวิชายังเลือกจากประวัติตามสิทธิ์
- ตรวจ attendance ชัดเจน, รีวิว 3 ระดับ, preview PDF จริง และยืนยันแบบ atomic/idempotent
- จัดข้อความ/กระดาษ/รูปในฉบับร่างก่อนยืนยัน, 8 handles, aspect toggle, crop/rotate, undo/redo และ stable image ID
- Revision snapshot และ export queue สำหรับ PDF รวมรายสัปดาห์/ZIP ตามตัวกรอง พร้อม progress/retry/expiry และตรวจสิทธิ์ดาวน์โหลด
- ทดสอบหน้าจริงแยกฐาน MySQL QA โดยใช้รายชื่อและรูปสังเคราะห์; ข้อมูล production สำรองก่อนเพิ่มตารางและไม่ใช้เป็นข้อมูลทดลอง

### ขอบเขตที่ยังต้องยืนยันก่อนเปิดใช้งานทั้งสถานศึกษา

- Contract/การเข้าถึง API รายวิชาจริง และทดสอบ API นักศึกษาภายนอกบนเครือข่ายใช้งานจริง
- แม่แบบที่ครูเลือกใช้ซ้ำ/คัดลอกโครงสัปดาห์ก่อน และ feature flag rollout ยังไม่ได้เพิ่มในรอบนี้
- ยังไม่ได้วัด p50/p95 บนข้อมูลขนาดใหญ่หรือทดสอบอุปกรณ์สัมผัสจริงทุกประเภท
- ตัวจัดเอกสารรองรับองค์ประกอบของบันทึกหลังสอน ไม่ใช่โปรแกรม Word แบบเต็มรูปแบบ

### ผลตรวจหลังพัฒนา 17 ตุลาคม 2569

- Automated suite: 60 tests / 523 assertions ผ่าน; TypeScript และ production build ผ่าน
- Browser QA แยก MySQL: เลือกกลุ่ม/วิชา/รายชื่อ อัปโหลด 2 รูป เปิดร่างต่อ จัดรูปด้วยเมาส์จริง ปลดล็อกยืดสองแกน undo/redo บันทึก layout รีวิว PDF ครบ 3 ระดับและยืนยันสำเร็จ
- Queue/ดาวน์โหลดจริง: PDF รวม 7 หน้าและ ZIP มี PDF ครบ 3 รายการ พร้อม CSV; เรนเดอร์และอ่านตรวจครบทั้ง 7 หน้า อีกชุดทดสอบ portrait/landscape ข้อความยาวตรวจครบ 8 หน้า
- Mobile 390px / desktop 1440px, light/dark ตรวจการล้นและความชัดเจนของปุ่ม/ข้อความ
- API ที่ตั้งค่าในเครื่องตอบ source `student_api` สำเร็จ: ตรวจบัญชีครูตัวอย่างหนึ่งบัญชี ได้กลุ่ม 6 กลุ่มและรายชื่อกลุ่มตัวอย่าง 3 คน ไม่ได้ตรวจครบทุกครู/ทุกกลุ่ม
- Production migration แบบเพิ่มตารางสำเร็จ; health check ข้อมูลเดิม 12 บันทึก/32 รูป/133 attendance ไม่เปลี่ยน และไม่พบ orphan/duplicate/missing image
- พบและแก้ rate limit ที่ทำให้ดู PDF ครบ 3 ระดับแล้วส่งออกต่อไม่ได้ โดยแยก preview กับ export limiter พร้อม regression test

## 1. ผลลัพธ์ที่ต้องการ

ครูทำบันทึกประจำสัปดาห์ครบ 3 ระดับได้ในพื้นที่ทำงานเดียว เลือกข้อมูลจากแหล่งที่มีอยู่ ตรวจรายชื่อ เขียนผลหลังสอน จัดรูป ตรวจเอกสารจริง แล้วจึงยืนยันบันทึกและดาวน์โหลด PDF ได้ โดยกลับมาแก้ไขต่อได้ชัดเจน

คง Laravel + MySQL + React 19 + TypeScript + Inertia 3 + Tailwind + shadcn/ui ที่ติดตั้งอยู่แล้ว การเปลี่ยนเทคโนโลยีอีกครั้งไม่ใช่งานจำเป็นสำหรับแก้ปัญหาที่พบ

ใช้หลัก UI จาก emil-design-eng: ค่าเริ่มต้นที่เหมาะสม ปุ่มและสถานะที่ชัด การตอบสนองทันที การลากที่ไม่กระโดด การใช้แป้นพิมพ์ และเครื่องมือที่แสดงตามสิ่งที่เลือก ส่วน PDF ใช้การเรนเดอร์เป็นภาพเพื่อตรวจผลจริงทุกหน้า

## 3. รูปแบบการใช้งานใหม่

เส้นทางหลัก:

`เลือกสัปดาห์ → กรอก/แก้บันทึก 3 ระดับ → รีวิวข้อมูลและจัดเอกสาร → ยืนยันบันทึก → เปิด/ดาวน์โหลด PDF`

### หน้าแรก: งานของฉัน

- ปุ่ม “สร้างบันทึกหลังสอน” เด่นจุดเดียวในเนื้อหาหลัก
- รายการจัดกลุ่มตามปี ภาคเรียน และสัปดาห์ เห็นสถานะทั้ง 3 ระดับพร้อมกัน
- แยก “ฉบับร่าง”, “พร้อมตรวจ”, “ยืนยันแล้ว” จากสถานะสร้างไฟล์ PDF
- งานล่าสุดมี “ทำต่อ” โดยไม่ต้องค้นข้อมูลใหม่
- ตัวกรองที่ใช้ดาวน์โหลดแสดงบนปุ่มหรือแผงส่งออกชัดเจน เช่น “สัปดาห์ 10 / ภาค 1 / 2569”
- มุมผู้ดูแลใช้โครงเดียวกัน เพิ่มตัวเลือกตำบลและสรุปงานที่ยังไม่ครบ

### พื้นที่ทำบันทึก

- ข้อมูลสัปดาห์กรอกครั้งเดียว และจำค่าปี/ภาคเรียนที่ผู้ใช้เลือกล่าสุดอย่างเหมาะสม
- ซ้ายเป็นรายการ 3 ระดับพร้อมสถานะและสิ่งที่ขาด กลางเป็นเนื้อหาที่กำลังทำ ขวาเป็นสรุป/Preview เมื่อพื้นที่พอ
- บนมือถือเป็นคอลัมน์เดียว แสดงรายการระดับแบบเลือกสั้น ๆ และเปิด Preview เต็มพื้นที่เมื่อร้องขอ
- แบ่งส่วนชัดเจน: กลุ่มและวิชา, ผู้เรียน, ผลหลังสอน, รูปภาพ, รีวิวเอกสาร
- หน้าสร้างและหน้าแก้ใช้ editor ชุดเดียวกัน
- ปุ่มประจำด้านล่าง: “บันทึกร่าง” และ “ตรวจสอบก่อนยืนยัน”; หลังผ่านรีวิวเป็น “ยืนยันบันทึก”
- แสดง “กำลังบันทึก”, “บันทึกร่างแล้ว เวลา ...”, “ยังบันทึกไม่สำเร็จ” และลองใหม่ได้
- การเก็บร่างอัตโนมัติหมายถึงเก็บข้อมูลส่วนตัวบน server แล้ว แต่ยังไม่ใช่รายการยืนยันในรายงาน ใช้ข้อความนี้ใน UI ให้ชัด

### ลดการกรอก

- ครูเห็นกลุ่มของตนเอง ผู้ดูแลเลือกตำบลก่อนแล้วโหลดตัวเลือกใน scope นั้น
- เลือกกลุ่มแล้วเติมชื่อ/รหัสและรายชื่อ; เปลี่ยนกลุ่มต้องแจ้งผลต่อรายชื่อที่เลือกไว้
- ค้นหากลุ่ม/วิชาได้ทั้งชื่อและรหัส แสดงแหล่งข้อมูลจริง
- มี retry และเวลาอัปเดตล่าสุด กรณีแหล่งภายนอกล่มใช้ข้อมูลสำรองพร้อมป้ายกำกับ
- ตรวจ pagination ของ API เพื่อไม่ทำให้รายชื่อเกิน 1,000 คนหรือหน้าถัดไปตกหล่น
- attendance เลือกมา/ขาดและวิธีเรียนได้รายคนหรือเป็นชุด พร้อมค้นหาและกรอง
- คำนวณยอดจากรายชื่อเป็นหลัก กรณีบันทึกแบบนับจำนวนต้องเลือกโหมดชัดเจนและแสดงว่าไม่มีบัญชีรายชื่อ
- คัดลอกโครงสัปดาห์ก่อนเฉพาะกลุ่ม/วิชาและแม่แบบ ห้ามคัดลอกสถานะมาเรียนให้เป็นข้อเท็จจริงของสัปดาห์ใหม่อัตโนมัติ
- ไม่แต่งผลการสอนให้เป็นข้อเท็จจริง ครูต้องเขียนหรือเลือกข้อความที่ตรวจแล้วเอง

### รีวิวก่อนยืนยัน

- เห็นสรุปทั้ง 3 ระดับ: วิชา กลุ่ม วันสอน ยอดมาเรียน รูป และเนื้อหาหลังสอน
- ข้อผิดพลาดมีปุ่มกลับไปยังระดับและช่องที่ต้องแก้ ไม่แสดงเพียงข้อความรวม
- เปิดดูรายชื่อเต็มและรูปขนาดใหญ่ได้
- มี “จัดเอกสาร” และ “ดู PDF ที่จะได้จริง” ก่อนยืนยัน
- ยืนยันแบบ atomic ทั้ง 3 ระดับตามกติกาเดิม; ร่างแยกเก็บทีละระดับได้
- ถ้า PDF สร้างไม่สำเร็จ บันทึกร่างยังอยู่และลองสร้างใหม่ได้
- หลังยืนยันแสดงลิงก์ “แก้ไขฉบับนี้”, “เปิด PDF”, “ดาวน์โหลด PDF” พร้อม revision ของเอกสาร

## 4. ตัวจัดรูปภาพและเอกสาร

### โหมดใช้งานทั่วไป

- อัปโหลดแล้วเห็น thumbnail ทันที เพิ่ม/แทนที่/นำออก/เรียงลำดับได้
- จัดเรียงอัตโนมัติด้วยแม่แบบ 2 รูปหรือ 4 รูปตามกติกาปัจจุบัน
- ตรวจชนิด ขนาด และแนวภาพก่อนอัปโหลด; server ตรวจซ้ำเสมอ
- แก้ EXIF orientation และสร้าง thumbnail สำหรับหน้าเว็บ แยกไฟล์ที่ใช้พิมพ์จากไฟล์ย่อ
- เก็บต้นฉบับและ transformation แบบไม่ทำลายไฟล์ เพื่อกลับไปแก้ได้
- รูป 1 หรือ 3 รูปอยู่ในร่างได้; ตอนยืนยันให้ใช้กฎ 0/2/4 เหมือนกันทุก endpoint จนกว่าจะมีการเปลี่ยนข้อกำหนดนี้โดยชัดเจน
- ตั้งต้นรักษาสัดส่วน; ผู้ใช้เลือก “ยืดอิสระ” ได้โดยตรง

### โหมดจัดละเอียด

- มี 8 จุดจับ รอบกรอบรูป และแถบเครื่องมือเมื่อเลือกรูป
- แยก 3 งาน: ขนาดกรอบ, ครอบภาพภายในกรอบ, และยืดภาพ
- สวิตช์ “ล็อกสัดส่วน”, หมุน, จัดซ้าย/กลาง/ขวา, เรียงหน้า/หลัง และนำกลับเข้าหน้า
- ปรับตัวเลขได้ แต่แสดงหน่วยมิลลิเมตร/เซนติเมตรที่สัมพันธ์กับกระดาษ ไม่บังคับให้ครูคิดเป็น pixel
- มี undo/redo และรีเซ็ตเฉพาะรูป; การเปลี่ยนแม่แบบเป็นหนึ่ง undo step
- drag ใช้ pointer capture และป้องกัน multi-touch แทรก; cancel กลับสู่ค่าก่อนลาก
- เปลี่ยน zoom แล้วระยะเมาส์ต้องแปลงกลับเป็นพิกัดเอกสารอย่างถูกต้อง
- ไม่ให้ iframe โหลดใหม่กลางการลาก ไม่ให้ selected object และ scroll หายเมื่อปรับค่า
- มี snap guides เปิด/ปิดได้ และคำเตือนรูปซ้อน/หลุดพื้นที่ โดยอนุญาตจัดทับเมื่อผู้ใช้ตั้งใจ
- โหมดล็อก ratio ใช้ scale เดียวทั้งสองแกนแม้ชนขอบ; โหมดยืดปรับแต่ละแกนได้อิสระ

### เค้าโครงเอกสาร

- A4 แนวตั้ง/แนวนอน ระยะขอบ และแม่แบบมาตรฐานตั้งค่าได้
- สวิตช์เปิด/ปิดหน้ารูปภาพ หน้ารายชื่อ และส่วนลายเซ็น หากเปิดลายเซ็นต้องไม่เปลี่ยนเป็นการลงนามดิจิทัลโดยอัตโนมัติ
- แสดง thumbnail และจำนวนหน้าจริง, fit page, fit width, zoom และปุ่มไปหน้าก่อน/ถัดไป
- เนื้อหาหลังสอนแบ่งหน้าตามการไหลของข้อความ ส่วนรูปและลายเซ็นจัดตำแหน่งได้ในพื้นที่ที่กำหนด
- แม่แบบที่ใช้งานทั่วไปต้องพิมพ์ได้ทันที การจัดละเอียดเป็นทางเลือก
- เป้าหมายคือความคุ้นเคยแบบ Word สำหรับงานบันทึกหลังสอน ไม่ขยายเป็นตัวแก้เอกสารอเนกประสงค์ทุกชนิด

## 5. โครงสร้างข้อมูลและการบันทึก

### แหล่งข้อมูลเดียว

1. Draft เก็บเนื้อหาที่กำลังแก้ รายชื่อ รูป และ layout ของแต่ละระดับในชุดงานสัปดาห์เดียว
2. Editor กับหน้ารายละเอียดใช้ข้อมูลเนื้อหาจาก draft/revision เดียวกัน ไม่เก็บข้อความคนละฉบับโดยไม่บอกผู้ใช้
3. Layout เก็บ paper, page/section toggles, imageId, x/y/width/height, rotation, crop, objectFit และลำดับชั้น
4. ผูก layout กับ imageId ที่คงที่ แทน image_1/image_2 ที่เปลี่ยนเมื่อสลับหรือลบรูป
5. เมื่อยืนยัน เก็บ immutable snapshot และ revision ของเนื้อหา รูป layout และแม่แบบที่ใช้ เพื่อพิมพ์ฉบับเดิมซ้ำได้
6. แก้ไขฉบับยืนยันสร้าง revision ใหม่ พร้อมเทียบกับฉบับเดิมก่อนยืนยัน

### ตาราง/field ที่คาดว่าจะเพิ่ม

- `teaching_drafts`: owner, scope ตำบล/สัปดาห์, schema_version, payload, lock_version, last_saved_at และ record/revision ที่เป็นต้นทาง
- `record_revisions`: record/submission, revision, snapshot, ผู้แก้, เวลา และเหตุผลแก้เมื่อจำเป็น
- `record_images`: เพิ่ม stable sort_order, dimensions, storage metadata และข้อมูลไฟล์ย่อแบบ nullable
- `record_document_layouts`: เพิ่ม schema_version และรองรับ layout ต่อ imageId; legacy adapter ยังอ่าน settings/content เดิมได้
- `export_jobs`: owner, authorized scope, revision/hash, สถานะ queued/processing/ready/failed, progress, path และวันหมดอายุ
- ตรวจ query และ EXPLAIN บน MySQL ก่อนเพิ่ม index; ระบบมี index scope/period/attendance อยู่แล้ว ไม่เพิ่มซ้ำโดยคาดเดา

### ความถูกต้อง

- autosave ส่งหลังหยุดพิมพ์ช่วงสั้น ๆ; ระหว่างลากไม่ยิง save ทุก pointer event
- ใช้ optimistic locking: หากอีกแท็บบันทึก revision ใหม่ ให้เทียบ/โหลดใหม่แทนเขียนทับเงียบ ๆ
- finalize ใช้ transaction, idempotency และ unique scope เดิมเพื่อกันส่งซ้ำ
- เมื่อแก้ปี/ภาค/สัปดาห์ต้องเปลี่ยนชุด parent อย่างถูกต้อง ไม่แก้แค่ record จน parent กับลูกไม่ตรงกัน
- การยืนยันต้องตรวจกลุ่ม ผู้เรียน รูป และตำบลร่วมกันบน server ไม่เชื่อค่าจาก client อย่างเดียว
- เพิ่ม FormRequest/DTO และบริการร่วม ให้กฎ create, update และ legacy compatibility ตรงกัน
- ร่างกับไฟล์ชั่วคราวต้องมีอายุและ cleanup ที่ไม่ลบรูปที่ revision ใดกำลังใช้อยู่

## 6. API และ PDF

### API

- รวม normalization, level mapping, fallback และ cache ไว้ใน StudentDirectoryService/adapter เดียว
- สัญญาข้อมูล options: items, source, fetched_at, stale, pagination, error_code และข้อความที่ครูเข้าใจได้
- แยก “ไม่พบรายชื่อ”, “กำลังใช้ข้อมูลสำรอง” และ “เชื่อมต่อไม่ได้” เป็นคนละสถานะ
- ตรวจแหล่งรายวิชา/รหัสวิชาจริงจาก integration ที่มี; ถ้าปลายทางไม่มีให้ใช้ catalog ที่ดูแลได้และประวัติ โดยไม่อ้างว่าเป็นข้อมูล API
- ห้ามส่ง API key ลงหน้าเว็บ และไม่ลดขอบเขต role เพื่อแก้ปัญหารายชื่อไม่ขึ้น
- ทดสอบ API ด้วย fixtures หลาย payload และ smoke test ปลายทางจริงเมื่อระบบนั้นพร้อม โดยไม่เก็บข้อมูลส่วนบุคคลใน test artifacts

### เส้นทางเอกสารเป้าหมาย

`Draft/Revision + Template version + Layout → Document snapshot → HTML/CSS renderer เดียว → PDF → Preview/Download/Print`

- React แสดง editor ที่ปรับได้ทันที ส่วน “ดู PDF จริง” ใช้ไฟล์ที่สร้างจาก snapshot/revision เดียวกับที่จะดาวน์โหลด
- ไม่ใช้ PDF test renderer คนละตัวเป็นหลักฐานรับรองเอกสาร production
- วัดจำนวนหน้าจากผล renderer จริง และแก้ pagination สำหรับข้อความไทยยาว ตารางรายชื่อ และส่วนลายเซ็น
- รอ font และรูปพร้อมก่อนสร้างไฟล์ แทนพึ่งเวลารอคงที่อย่างเดียว
- เอกสารรายเดียวอาจสร้างทันทีถ้าเร็วพอ; PDF รวม/ZIP ทำงานผ่าน queue พร้อม progress และ retry เฉพาะรายการที่ล้มเหลว
- จัดคิวงานตามสิทธิ์และจำกัด concurrency เพื่อไม่เปิด Chrome พร้อมกันเกินทรัพยากร
- cache โดย content/layout/template/image revision และ scope; เมื่อข้อมูลเปลี่ยนต้องสร้างฉบับใหม่
- หน้า Preview แจ้งเมื่อข้อมูลใหม่กว่าฉบับที่กำลังแสดง และไม่ให้ยืนยันว่าเป็นฉบับล่าสุดผิด ๆ
- กำหนด export scope ชัดเจน: รายบันทึก, รายสัปดาห์, ทั้งหมดตามตัวกรอง; ระบุ PDF รวมกับ ZIP ให้ผู้ใช้แยกออก
- ลิงก์ดาวน์โหลดตรวจเจ้าของและสิทธิ์ปัจจุบัน มีอายุ ไม่อาศัยรู้ชื่อไฟล์อย่างเดียว
- ให้ Laravel migrations เป็นเจ้าของ schema; ค่อยย้ายการสร้าง schema ออกจาก request/render ผ่าน config.php หลัง adapter พร้อม

## 7. แนวทางภาพลักษณ์ใหม่

- บุคลิกเรียบ สุภาพ ใช้งานประจำวันได้ สีพื้นสว่าง สีเขียวหลักเดิมปรับให้เป็นระบบเดียว ลดกล่องซ้อนและเงาหนัก
- ฟอนต์ UI ภาษาไทยอ่านง่าย คงตัวเลือกฟอนต์เอกสารราชการสำหรับกระดาษ
- ปุ่มหลักหนึ่งงานต่อบริบท: สร้าง, ตรวจ, ยืนยัน หรือดาวน์โหลด
- เครื่องมือรูปแสดงเมื่อเลือกรูป เครื่องมือลายเซ็นแสดงเมื่อเลือกส่วนลายเซ็น
- เปลี่ยนข้อความเทคนิค เช่น Student API เป็น “ข้อมูลนักศึกษาจากระบบกลาง” พร้อมรายละเอียดแหล่งข้อมูลในส่วนรอง
- error ข้างช่อง, error summary ที่กดไปช่องได้, keyboard focus, label/input IDs และปุ่มสัมผัสอย่างน้อยประมาณ 44px
- ใช้ theme tokens ของระบบเดิมทั้ง light/dark และทดสอบสองโหมด; กระดาษ Preview แสดงสีจริงของเอกสารเสมอ
- animation เฉพาะเพื่อบอกสถานะ ไม่มีการหน่วงการพิมพ์ การเลือกชื่อ หรือการขยับด้วยคีย์บอร์ด

| ชุดงาน | งานหลัก | สิ่งที่ส่งให้ตรวจ | เกณฑ์ผ่านก่อนทำชุดถัดไป |

| 0. เก็บฐานเทียบ | inventory API, ข้อกำหนดเอกสาร, ตัวอย่างเนื้อหาสั้น/ยาว, รูปและรายชื่อแบบไม่ระบุตัวบุคคล | mapping ปัจจุบัน, PDF อ้างอิง, ชุดข้อมูลทดสอบ และภาพเส้นทางใหม่ | ยืนยันหน้าที่ต้องมีและรักษารูปแบบทางการเดิมได้ |

## 9. เกณฑ์ทดสอบรับงาน

### บันทึกและ API

- เปิดสร้างใหม่ กรอกทีละระดับ บันทึกร่าง รีเฟรช กลับมาทำต่อ และแก้หลังยืนยัน
- โหลด API สำเร็จ/ช้า/ล่ม/ไม่มีข้อมูล/มีหลายหน้า และ fallback ที่ส่ง level ชื่อไทย
- สลับกลุ่มเร็ว เปลี่ยนตำบลของผู้ดูแล รายชื่อต้องไม่ปนคำขอก่อนหน้า
- ตรวจชื่อ/รหัสไม่ซ้ำ ยอดรวมตรงรายการจริง และเลือกวิธีเรียนได้
- ยืนยัน 3 ระดับแบบ atomic, ส่งซ้ำ, สัปดาห์ซ้ำ, แก้ scope และเปิดแก้พร้อมกัน 2 แท็บ
- ข้อผิดพลาดต้องคงร่างกับรูปที่อัปโหลดแล้ว ไม่เริ่มกรอกใหม่ทั้งหมด

### รูปและเอกสาร

- รูป 0/2/4 ตอนยืนยัน, 1/3 ในร่าง, รูปแนวตั้ง/แนวนอน/จัตุรัส/EXIF และไฟล์เกินขนาด
- ลากทั้ง 8 จุดจับที่ zoom หลายระดับ ปรับ width/height แยก หมุน ครอบ สลับภาพ และ undo/redo
- เปิด lock แล้ว ratio ไม่เสียเมื่อชนขอบ; ปิด lock แล้วยืดได้ทั้งสองแกน
- เปลี่ยนกระดาษหรือระยะขอบแล้วตรวจ safe area ของรูปเดิม
- สลับลำดับ/ลบรูปแล้ว layout ยังตามรูปที่ถูกต้อง
- แก้ข้อความแล้ว preview/save/download ต้องตรงกัน โดยไม่ถูก override เก่าทับ
- ข้อความไทยสั้น/หลายหน้า, รายชื่อเกินหนึ่งหน้า, รูปหาย, ฟอนต์โหลดช้า และเปิด/ปิดหน้าทุกชุด
- เรนเดอร์ PDF เป็นภาพและตรวจทุกหน้า; เปรียบเทียบภาพอ้างอิงด้วย tolerance สำหรับ anti-aliasing และอ่านตรวจภาษาไทย
- ตรวจ crop/rotate/text ทุกหน้าใน PDF จริง ไม่ตรวจเพียงว่าไฟล์ขึ้นต้นด้วย %PDF

### ความเร็วและการเข้าถึง

- ตั้ง baseline ก่อนปรับ แล้วรายงาน p50/p95 ของโหลดหน้า options, save draft และ export พร้อมระบุเครื่อง/จำนวนข้อมูล
- เป้าหมายการตอบสนองการลาก: เห็นผลใน frame ถัดไปบนเครื่องทดสอบ, ไม่มี HTTP request ต่อ pointermove
- เป้าหมาย draft save: ตอบกลับภายในประมาณ 1 วินาทีบนเครื่อง/เครือข่ายทดสอบปกติ โดยแยกเวลารอ debounce ออก
- export จำนวนมากแสดง job/progress ได้ทันที ไม่รอจนไฟล์ทั้งหมดเสร็จใน request เดียว
- ทดสอบ desktop/tablet/mobile, keyboard, focus, label และ light/dark
- ตรวจทุก endpoint ใหม่ด้วย district และ tambon รวมถึง print, preview, upload, draft และ download ข้ามตำบล

## 10. การย้ายข้อมูลและขอบเขตที่ต้องตรวจเพิ่ม

- สำรองฐานข้อมูลและไฟล์ก่อน migration; ไม่แก้หรือลบ uploads จริงเพื่อทดลอง UI
- migration เพิ่ม field/table แบบ additive ก่อน แล้ว backfill แบบ dry run
- หาก legacy content override ต่างจากข้อมูลหลัก ให้แสดงความต่างและเลือกฉบับที่ต้องการเป็นรายบันทึก ไม่เขียนทับทั้งระบบอัตโนมัติ
- mapping image_1..4 ไป imageId ต้องเก็บลำดับเก่าไว้ทวนสอบ
- เปิด workspace ใหม่ด้วย feature flag เป็นกลุ่มเล็กก่อน และ rollback การใช้งานได้โดยร่าง/ฉบับเดิมยังอยู่
- ปลายทาง API รายวิชาและรูปแบบบังคับของเอกสารยังต้องตรวจจากระบบ/ตัวอย่างที่มีเมื่อเริ่มชุดงาน 0 แผนนี้ไม่สมมติว่ามี endpoint รายวิชาแล้ว
- ความรับผิดชอบต่อบันทึกคง scope district/tambon เดิม; หากต้องการสิทธิ์ส่วนตัวรายครู ต้องตกลงเพิ่มก่อนเปลี่ยน authorization
